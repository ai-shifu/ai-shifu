# Local storage response safety

## Purpose / Big Picture

Prevent uploaded or historical local files from executing active documents in
the application origin while preserving course images, branding, avatars, and
TTS playback. Coordinate the private fix and release for GHSA-29h3-2gcr-x7f9.

## Surprises & Discoveries

- Course covers parse the resource ID from the URL basename. Changing storage
  keys independently from resource IDs would break existing cover resolution.
- Creating an unknown supplied resource ID is deliberate compatibility, with
  an existing regression test. It need not change to close the rendering boundary.
- Private security forks cannot run GitHub integrations or CI. Local checks
  and independent review must provide the pre-merge verification evidence.
- Historical files require a read-side fix, irrespective of upload validation.

## Context and Orientation

`src/api/flaskr/service/shifu/funcs.py` accepts a caller-supplied resource ID as
an object key. `service/common/storage.py` writes original bytes locally.
`route/storage.py` formerly guessed MIME from the key before checking bytes
and served every object inline. Bundled Nginx shares the storage and web origin,
where the browser-readable session token resides. The affected release range
starts at v1.2.1, which introduced local storage.

## Validation and Acceptance

No attacker-controlled filename or bytes may produce an active document MIME
on the application origin. Unknown content must be an attachment with binary
MIME; every served file must carry nosniff and a sandbox without script or
same-origin permissions. Existing image/icon/audio bytes and resource-ID
round trips remain usable, including range and cache revalidation responses.
The security regression must fail before the fix and pass after it. Release
completion additionally requires fixed-version availability and advisory/CVE
state readback.

## Interfaces and Dependencies

The storage HTTP response contract changes for active or unknown content only.
Supported inline media are JPEG, PNG, GIF, WebP, ICO, and MPEG audio, matching
current repository producers. No new dependency, schema, configuration,
frontend interaction, or analytics contract is introduced.
