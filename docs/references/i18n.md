# Internationalization (i18n) Guide

This consolidated guide explains how i18n works across the repository (Backend API + Cook Web), how to add or modify translations, and how validation is enforced in CI and lefthook.

## Overview
- Shared, canonical translations live in `src/i18n/<locale>/**/*.json`.
- Every JSON file may use two helpers:
  - `__namespace__`: explicit namespace (recommended)
  - `__flat__`: flat key/value map under that namespace
- Locale metadata and declared namespaces are in `src/i18n/locales.json`.
- Cook Web consumes shared JSON via a lightweight API bridge and i18next; Backend loads the same JSON at startup.

## Directory Structure
- `src/i18n/en-US/**`: English
- `src/i18n/es-ES/**`: Spanish (Spain)
- `src/i18n/zh-CN/**`: Chinese
- `src/i18n/fr-FR/**`: French
- `src/i18n/ar-SA/**`: Arabic (Saudi Arabia, RTL)
- `src/i18n/th-TH/**`: Thai
- `src/i18n/locales.json`: Default locale, supported locales, and exported namespaces

## Namespaces & Key Style
- server.<domain>[.<subdomain>].<key>
  - Backend business and error messages. Example: `server.order.courseNotPaid`.
- module.<feature>[.<subfeature>].<key>
  - Frontend module UIs and flows. Example: `module.chat.copySuccess`.
- component.<name>[.<part>].<key>
  - Reusable UI components. Example: `component.header.title`.
- common.core|errors|language
  - Cross-cutting strings. Example: `common.core.submit`.

Key rules
- Dot-separated. Lowercase namespace segments. lowerCamelCase keys.
- Clear, action-oriented names. English-only for keys.
- Avoid positional placeholders; prefer named placeholders with ICU.

## Chinese Terminology
- Do not use `创作者` as a generic product term in Chinese user-facing text or
  Chinese docs.
- Use `老师` when referring generally to course-building users, teacher accounts,
  billing accounts, wallets, subscriptions, notifications, and operator-facing
  account lists.
- Use `课程负责人` when referring to the owner of a specific course. Inside an
  existing course context, `负责人` is acceptable when it reads more naturally.
- Keep English and French translations aligned with the same distinction: use
  `teacher` / `enseignant` for the generic role, while a specific course owner
  may still be translated as `creator` / `créateur`.
- Keep technical contracts unchanged: do not rename keys, symbols, routes,
  database fields, `creator_bid`, `Creator Bid`, or existing `creator*`
  identifiers unless a dedicated compatibility migration explicitly requires it.

## ICU MessageFormat (placeholders)
- Use ICU everywhere to align API and frontend formatting.
  - Variables: `Hello, {name}`
  - Plurals: `{count, plural, one {# item} other {# items}}`
  - Dates/times: `{ts, date, medium}` / `{ts, time, short}`
- Placeholders must match across locales for the same key. Validation enforces this.

## Add or Modify Keys
1) Choose file/namespace
   - Backend: `server.<domain>` (e.g., `server.user`, `server.order`, `server.shifu`)
   - Frontend: `module.*` or `component.*`
2) Edit every supported locale
   - Update the corresponding file under every locale listed in
     `src/i18n/locales.json`.
3) New namespace?
   - Create it in every supported locale and ensure it is included in `locales.json` (or run the generator below).

## Product Locale Delivery Checklist

Use this checklist before calling a new product language complete. A parity
check alone cannot catch untranslated behavior, incorrect product meaning, or
content marked with the interface language instead of its own language.

1. **Set the exact scope and translation source.** Choose one locale code and
   regional variant. Use the Chinese source value and its production call site
   to determine meaning; compare existing locales when context helps. Review
   product terms, billing validity periods, action labels, and error recovery
   instructions with the owning flow. Translate user-visible values without
   changing keys, required ICU argument names, Markdown/HTML or link syntax,
   technical identifiers, or authored course data. Use plural categories for
   the target language, and change a link destination only when an approved
   localized target exists. Do not treat a successful string substitution as
   proof that the message means the right thing in context.
2. **Inventory all application-owned surfaces before writing translations.**
   Match every shared JSON file and key under `src/i18n/<locale>/` to the
   current locale inventory. Search production call sites and explicit locale
   unions, normalizers, allowlists, request validation, and configuration in
   Cook Web and Backend. Cover language selection and persistence, API errors,
   email, billing, onboarding, course authoring, and legal URL/page behavior.
   If approved legal text is unavailable, label the fallback language instead
   of presenting another language's document as a translation. Check number,
   date, currency, and direction formatting where the new locale changes them.
3. **Check persisted multilingual content separately.** Configuration or
   prompts saved before a locale is added may not gain the new translation from
   JSON changes. If a backfill is necessary, make it previewable and
   idempotent, preserve existing custom translations, guard against concurrent
   changes, and document the per-environment rollout step. Do not silently
   rewrite authored lessons or other saved user content.
4. **Keep language ownership explicit.** Interface locale, authored title
   language, and lesson/content language can differ. Trace each through the
   API and every relevant display: catalog, tooltip, desktop and mobile
   headings, fullscreen player, print/PDF, body text, and authored interaction
   choices. Apply a known content language to its text. Do not infer unknown,
   system-generated, or user-authored content language from the interface,
   character script, or component-control locale. Verify HTML `lang` and
   `dir`, especially RTL, with representative browser or accessibility checks.
5. **Honor the dependency boundary.** Product translation does not include a
   dependency library's own UI translations, cross-repository PR, package
   publication, or version bump solely for localization. That library can be
   translated later in its own task. Integrate only with the currently pinned
   package's supported locale contract; document unsupported controls and
   their actual fallback. Keep host-owned content language separate from the
   library's control locale.
6. **Account for new user actions and verify the complete flow.** If adding a
   language introduces a new selection path or changes an existing one, define
   or extend its product analytics contract and cover accepted choices,
   exclusions, deduplication, and tracking failure without blocking selection.
   Run translation parity and usage checks, regenerate locale metadata and
   frontend key types when needed, and test the affected frontend and backend
   paths. Run type checking, lint, build, and a browser smoke when routing,
   direction, or visible fallback behavior changes. Before committing, follow
   the repository tooling and all-files gate in `AGENTS.md`.
7. **Recheck after rebases and before reporting completion.** Compare new
   source keys and changed call sites from `main`, translate any newly added
   messages, rerun the relevant checks, and state remaining legal, persisted
   data, or dependency-control limits in the PR. Verify the latest pushed head
   and CI rather than relying on checks from an earlier commit.

## Validation & CI
Run in repo root:

```bash
python scripts/check_translations.py
python scripts/check_translation_usage.py --fail-on-unused
python scripts/generate_languages.py && git diff -- src/i18n/locales.json
```

Enforced by lefthook and CI:
- Parity across locales (files and keys)
- ICU placeholders consistency across locales
- No missing or unused keys within declared namespaces
- locales.json matches current files
- Backend guard against hardcoded CJK in Python

## Cook Web Tooling
- i18next with ICU enabled in `src/web/src/i18n.ts`
- Unified fetch backend: `src/web/src/lib/unified-i18n-backend.ts`
- Frontend user-facing locales are exported from `src/i18n/locales.json`
- Optional key typing for developer ergonomics:

```bash
node scripts/generate_i18n_keys.js
# writes src/web/src/types/i18n-keys.d.ts
```

## Backend Usage
- Use `_('server.domain.key')` for server messages; avoid hardcoded strings in code.
- Avoid legacy `module.backend.*` keys; use `server.*` exclusively.

## Scripts Summary
- Validate parity: `python scripts/check_translations.py`
- Validate usage: `python scripts/check_translation_usage.py --fail-on-unused`
- Generate locales metadata: `python scripts/generate_languages.py`
- Create namespace skeleton: `python scripts/create_translation_namespace.py <namespace> [--keys ...]`
- (Cook Web) Generate TS union of keys: `node scripts/generate_i18n_keys.js`

## Migration Notes (Phase 0 decisions, condensed)
- Canonical JSON under `src/i18n/` for all runtimes.
- ICU everywhere; frontend via i18next-icu; backend via Babel-compatible formatting.
- `locales.json` is the single source of truth for locale list + namespaces.
- CI + lefthook enforce parity, usage, and metadata freshness.
